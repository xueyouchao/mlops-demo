## Scope

A second estimator family behind the same tool, because the constraint was never the estimator and always the interface: `train_candidate` *was* one estimator with three fixed numbers, so "try a different kind of model" was not a call the agent could make and no version could say which family produced it.

- `model_kind` + a validated `params` object replace the three flat hyperparameters, with **per-kind validation** (unknown kinds, another kind's parameters, out-of-range values) returning a *verdict* the brain corrects in one step.
- Two kinds with deliberately different inductive bias: `gradient_boosting` (the trainer's original) and `logistic_regression` (a linear model on standardized features). A linear model cannot represent a split or an interaction, so agreeing with the trees says something about the data rather than about a re-tuned copy of the same model.
- The tool description is **generated from the kinds**, so a kind the trainer accepts is a kind the model is told about — the silent failure this prevents is a kind that exists but is never chosen.
- `read_run_metrics` reports an incumbent's kind and parameters, which is what lets the agent choose a family deliberately.

Invariants this build must not move: **one registry model name** (`breast-cancer-classifier` — both kinds log under it), **idempotency keyed on dataset + `model_kind` + params**, the **two-trainings-per-run cap**, and the **existing metrics** (`accuracy`, `roc_auc`) so the console and the agent's digest need no change.

**Done when:** both kinds train through the agent and register under the same model name, a repeat of identical parameters reuses the version rather than registering a second one, the cap still bites, the console reads both, and serving loads either artifact.

**Read with:** [Define the agent's tool surface & schemas](../tickets/T02-define-the-agent-tool-surface-and-schemas.md) (its second amendment is this build's interface), [Lock the run semantics](../tickets/T06-lock-the-run-semantics.md) (the cap and idempotency), [Build the six tool activities](../tickets/B03-build-the-six-tool-activities.md) (the trainer as built).

**Not** the map's out-of-scope *multi-model genericity*: there is still one model name, one registry, one promotion gate and one serving route. What varies is the estimator family behind the tool.

## Outcome

Files: `services/worker/model_kinds.py` (new — the kinds, their parameters and bounds, `coerce` for validation, `build` for construction, `describe`/`params_schema` for the schema), `services/worker/activities.py` (`train_and_register` takes `model_kind` + `params`, logs the kind and each of its parameters, still logs `accuracy`/`roc_auc`), `services/worker/tools.py` (`train_candidate` validates per kind and returns verdicts; the idempotency lookup is keyed on data + kind + params; `read_run_metrics` reports the kind's parameters), `services/worker/workflows.py` (`TrainingWfInput` carries kind + params, the console's three knobs map onto that kind's parameters), `services/worker/brain.py` (tool schema and one prompt rule generated from the kinds; the scripted probe is a call in the new shape), `services/worker/Dockerfile` (COPY the new module), `services/worker/test_brain.py` (+26 checks, before/after below), `README.md`.

**Both kinds, through the agent, one model name.** Run `agent-52f3be65` (7 steps, 23.2 s, producer `model`) trained `gradient_boosting` (`n_estimators=250, max_depth=3, learning_rate=0.06`) → **v44** · accuracy 0.9561 · roc_auc 0.9914, then `logistic_regression` (`C=0.5, max_iter=300`) → **v45** · accuracy 0.9825 · roc_auc 0.9957, evaluated both plus the incumbent v18 (0.8860 / 0.9471) and proposed v45 with the kind named in its rationale: *"v45 (logistic_regression, C=0.5, max_iter=300) … beats current production v18 on the identical held-out split"*. **Idempotency, on the new key.** A second run (`agent-3c12b055`) repeating the identical two calls got *"v44 already exists for exactly this model_kind and these parameters on this data — reused, no new version registered"* and the same for v45 — no new versions, same ids. The migration case is covered by the same lookup: re-asking for **v43**'s parameters (trained before `model_kind` existed, so its run has no such param) reused v43, which is why a missing `model_kind` is read as `gradient_boosting` rather than as a mismatch.

**The cap, live, and what it counts.** Run `agent-110886fc` (5 steps, 20.6 s) made three training calls: `gradient_boosting` (`n_estimators=350, max_depth=5, learning_rate=0.07`) → **v47**, `logistic_regression` (`C=1.5, max_iter=400`) → **v48**, then the first call's parameters again — which came back **`training_cap_reached`** (*"this run has already trained 2 candidates (cap 2); propose what you have or conclude"*), refused **before** the idempotency lookup could have answered it with v47, and the run concluded instead. Worth recording, because it is pre-existing behaviour this build preserved rather than invented: the counter rises only for a training that **registered a new version** (`workflows.py`: a reuse "is not a second training, so it does not spend the second slot"), which run `agent-3c12b055` shows from the other side — its third call created v46 because the two calls before it were reuses.

## Amendment — 2026-09-14: the console names the family too, and the kinds move to the shared package

The Outcome above closed with *"the console (no kind selector)"* listed as deliberately unchanged, and that was the right scoping call at the time — the asymmetry had been created by the agent's tool, and closing it there was the whole build. It is superseded here, on the human's instruction: **the operator can pick the estimator family now**, which makes the sentence in the README ("both human entry points train the gradient-boosting family, because their knobs *are* that kind's parameters") false, and the honest version of it is part of this change.

**The kinds changed address.** `services/worker/model_kinds.py` → `packages/ml_platform/model_kinds.py`. The reason is the request above: the api has to validate a `TrainRequest` against the same definitions the worker trains with, and to *generate* the console's panel from them. A second copy in the api is exactly the drift this module exists to prevent, and `packages/ml_platform` is already the shared tree — `COPY packages/ml_platform` is in the api, worker and serving Dockerfiles, `registry_health.py` is the precedent for a cross-service module there, and the module stays stdlib-only at import time (sklearn is imported inside `build`), which is why the api image needs no scikit-learn. Imports updated in `tools.py`, `activities.py`, `brain.py`; the worker image no longer carries a top-level copy, and `test_brain.py` puts `packages/` on `sys.path` for the host run.

**What the api grew, and what it did not.** `TrainRequest` gains `model_kind` (default `gradient_boosting`) and an optional `params` object, and keeps the three top-level knobs — now `int | None` with *no* bounds of their own, because the bounds live in `model_kinds` and are enforced by the resolution that module owns (`resolve_request`). An out-of-range knob is therefore one 400 in the trainer's own words rather than a second, drifting set of pydantic rules; a wrong type is still a 422. `GET /api/models/kinds` serves `model_kinds.catalog()`, which the panel renders — a family, a bound or a default cannot differ between what the panel shows and what the trainer does. The read model reports each version's family (`ModelVersion.model_kind`, read from the training run's `model_kind` param by `registry_sync`), and the console's version table names it, so a human can see which family produced a version.

**Workflow, deliberately minimal:** `TrainingWfInput.run` passes `model_kind` through as given and no longer substitutes the literal `"gradient_boosting"` — an empty kind is resolved by the *activity* (`model_kinds.DEFAULT_KIND`), so the name of the default lives in one module and `workflows.py` stays import-light (the sandbox reason its own docstring gives). The three-knob mapping stays, for a payload in the old shape.

**Verified live, through the console's own origin.** The old three-knob call (`n_estimators=150, max_depth=4, learning_rate=0.09`) still trains gradient boosting: **v50**, run params identical to v49's, metrics identical to the digit (accuracy `0.9473684210526315`, roc_auc `0.9874338624338624`). The shape the panel now sends — `{"model_kind": "gradient_boosting", "params": {…}}` with the same numbers — produced **v51** with byte-identical params and metrics, i.e. the two shapes are one training. `logistic_regression` (`C=0.5, max_iter=300`) produced **v52** at `0.9824561403508771` / `0.9957010582010581`, *identical to the agent-trained v45* from the Outcome above — one trainer, one split, one seed, whichever door. Eight bad payloads (unknown kind, another kind's parameter, `C=0`, `max_iter=5000`, `n_estimators=5000` as a knob and as part of a kind, `learning_rate=0`, non-object `params`, non-string kind) all came back **4xx in 3–9 ms** with the trainer's own sentence, and created no workflow at all; the activity still re-checks the same payloads as non-retryable `ApplicationError`s, because the agent reaches the trainer without passing through the route.

**Idempotency, on the same key, across the two doors.** The agent's `train_candidate` tool asked for exactly what the console had registered and *reused* it — `v52` for the linear model, and for gradient boosting `v51` (the lookup orders by start time, so two identical console trainings v50/v51 are twins and it answers with the newer one, as it always has) — with no new version: 52 before and after.

**Serving loads either family,** checked both ways: `mlflow.sklearn.load_model` in the serving image returned a `Pipeline['scale','clf']` for v52 and a `GradientBoostingClassifier` for v51, and moving real traffic (`POST /api/models/rollback`) made `POST /v1/predict` answer `{"model_version":"52",…,"routing":{"52":100}}` and then `{"model_version":"51",…}`, before traffic was returned to production **v45**.

**Tests.** `python3 services/worker/test_brain.py`: **96 → 96** checks, 0 failed (the module moved, nothing in it changed behaviour). `python3 -m unittest tests.test_domain -v`: **5 → 12** tests, OK — seven new ones for the vocabulary the api now shares (the old three-knob call resolving to the original training, the two shapes agreeing, unknown kind, out-of-range parameters, another kind's parameter, and the catalog carrying every spec key the panel is generated from).

**Registry, and the state left behind:** 49 → **53** versions — v50 (the old three-knob call), v51 (the panel's shape, same numbers), v52 (`logistic_regression` through the console) and v53 (the seed-trainer re-run, below); none promoted by hand. Production is the same version it was before this session's work began (v45, the read model re-hydrated by an api restart so it no longer carries the stale v18 production row), routing `{"45": 100}`, no promotion at the gate, every workflow `Completed`, and only one row in the read model reads `production`.

**Still deliberately not changed:** `services/serving`, the estimator for the original three numbers, the two-trainings-per-run cap, the human-approval gate, the agent's six-tool surface and its own training path. `scripts/train_and_register.py` keeps **no family selector** — the seed trainer stays gradient-boosting only, and the README now says so instead of implying otherwise — but it gained one line, `mlflow.log_param("model_kind", "gradient_boosting")`: without it the documented first-run path (seed trainer → console) would show a dash in the new `kind` column, which is a hole in the very feature this closes. Verified by running it (`--profile tools run --rm --build trainer`), which registered **v53** with the family in its run params.
